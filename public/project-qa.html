Overview

1How does this project work?

It's an AI-assisted mind-map builder. A Nuxt 4 single-page app where you sketch nodes on a hand-rolled SVG canvas, and AI "agents" analyze your map and stream back suggestions you can apply with one click.

The big picture

You draw on canvas  ->  click "Analyze"  ->  graph serialized to JSON  ->  POST /api/ai/analyze
                                                                                |
                                                            policy pipeline + LangGraph workflow
                                                                                |
        canvas updates  <-  apply suggestion  <-  SSE stream of events  <-  Fireworks.ai LLM

Frontend

  • pages/index.vue — the entire app. SSR disabled (ssr: false), state persisted to localStorage. No router beyond this one page.
  • components/MindMapCanvas.vue — hand-rolled SVG canvas. Interaction split into focused composables: useViewport, useNodeDrag, useLabelEditor, useTouchGestures.
  • Three Pinia stores (no single "facade" store):
    • useGraphStore — nodes, cross-links, selection, tool, undo/redo, debounced persistence.
    • useAIStore — streaming reasoning, suggestions, highlights, active agent.
    • useSettingsStore — accent colour (pushed to a CSS variable).
    • All refs wrapped in skipHydrate() — see Q5.

The AI request flow (the heart of the app)

  1. useAIAnalysis.analyze() serializes the map (lib/mindmap/serializer.ts: MindMapNode[] -> SerializedGraph) and POSTs to /api/ai/analyze. The Fireworks key travels in the x-fireworks-key header, never the body.
  2. server/api/ai/analyze.post.ts runs a strict policy pipeline before any LLM call: resolve key -> rate-limit (two-tier) -> validate (Zod, 50 KB cap, null-byte) -> moderation -> stream. Moderation is jailbreak regex + optional OpenAI moderation, fail-open, input-only.
  3. lib/ai/graph.ts runs a two-node LangGraph workflow: analyzerNode -> suggesterNode, each calling Fireworks.ai via the OpenAI-compatible SDK.
  4. Results stream back as Server-Sent Events. Wire format is the BoardStreamEvent union: thinking / suggestion / done / error.
  5. AIPanel.vue renders the live trace and a list of AISuggestionCard components.
  6. Clicking Apply runs lib/mindmap/applier.ts (applyAction), which mutates the graph store. AI actions: add_node, link_nodes, relabel, highlight, expand_branch, tidy_layout.

Key design choices

  • Single source of truth for types: Zod schemas in lib/ai/schemas.ts define everything; lib/ai/types.ts re-exports the inferred types. All constants live in lib/config.ts.
  • Security single-sourced: SECURITY_HEADERS applied by server/middleware/securityHeaders.ts, mirrored in vercel.json. CORS is exact-origin.
  • Rate limiting: in-memory for dev, Upstash Redis for prod, two-tier.
Architecture

2Is it built with LangChain?

Partly — and the distinction matters. The AI stack is two LangChain packages plus the OpenAI SDK:

@langchain/langgraph    orchestration (the workflow graph)
@langchain/core         peer dependency of langgraph
openai                  the actual LLM API calls
  • LangGraph handles only orchestration. lib/ai/graph.ts is a tiny state machine: START -> analyzer -> suggester -> END. StateGraph + Annotation.Root define a shared state; each node returns a partial update LangGraph merges.
  • The OpenAI SDK does the actual model calls. new OpenAI({ apiKey, baseURL }) points at Fireworks.ai's OpenAI-compatible endpoint — no ChatOpenAI wrappers, chains, prompt templates, retrievers, memory, or LangChain agents.

Built on LangGraph for orchestration, but talks to the LLM through the plain OpenAI SDK — not the LangChain model/chain layer.

It's small enough (two sequential nodes) that LangGraph is more scaffolding-for-future-growth than strictly necessary.

Code trace

3Where is POST /api/ai/analyze in the code?

The endpoint string is hidden behind constants in lib/config.ts, which is why a literal search for "/api/ai/analyze" in the frontend turns up nothing. The code-accurate flow:

AIPanel button @analyze
  -> handleForceAnalyze()              pages/index.vue:67
  -> analyze()                         composables/useAIAnalysis.ts:44
  -> serializeGraph(...)               useAIAnalysis.ts:53   (graph -> JSON)
  -> fetch(API_ROUTES.analyze, POST)   useAIAnalysis.ts:58   (/api/ai/analyze)
  -> readSseStream -> applyEvent       useAIAnalysis.ts:69   (events -> useAIStore)
  • API_ROUTES.analyze resolves to the /api/ai/analyze path.
  • HEADER_FIREWORKS_KEY resolves to the x-fireworks-key header name.
  • Both live in lib/config.ts; the literal path only appears there and as the server filename server/api/ai/analyze.post.ts.
Design decision

4Why hand-rolled SVG, not a canvas library?

The canvas imports only Vue + its own composables + lib/mindmap/geometry — zero drawing libraries (no Fabric, Konva, D3, Excalidraw, tldraw). ~360 lines total. The project pivoted off Fabric.js to this approach, part of a broader effort to shed dependencies.

  1. The aesthetic requires custom rendering anyway. Helpers like sketchRectPath, rotFor, edgePath produce a hand-drawn, sketchy look. A general canvas library gives crisp geometry you'd be fighting.
  2. SVG is declarative — it fits Vue. Nodes live in a reactive store; SVG elements are DOM, so Vue's reactivity drives them directly. A <canvas> library keeps its own scene graph, forcing you to sync two sources of truth.
  3. Free interactivity & accessibility. Each node is a real DOM element: pointer events, hit-testing, focus, inline text editing all come for free.
  4. Matches the repo's direction: less dependency weight for a single-board app.

Trade-off: DOM-based SVG gets slower than a <canvas> bitmap at thousands of nodes — but this is a single mind map, not a 10,000-object design tool, so that ceiling never gets hit.

Vue / SSR

5What is skipHydrate?

It solves an SSR hydration mismatch. The app runs briefly on the server then in the browser. Pinia normally serializes server state into the HTML and the browser rehydrates from it; if the two disagree, Vue warns.

The settings store reads localStorage (browser-only):

const accentColor = ref<string>(
  import.meta.client ? (localStorage.getItem(THEME_KEY) ?? DEFAULT_ACCENT) : DEFAULT_ACCENT
)

Server sees DEFAULT_ACCENT; browser may see a custom saved colour -> mismatch.

return { accentColor: skipHydrate(accentColor), setAccent }

skipHydrate = "this value is owned by the browser (localStorage), don't let the server's guess clobber it."

The wrinkle: the page is ssr: false, so there's technically no hydration step — skipHydrate is a belt-and-suspenders guard on every persisted ref, documenting intent and staying correct if SSR were ever re-enabled.

Code quality

6Is it OK for the store to hold all that logic?

Acceptable for this scale, but useGraphStore was wearing three hats: state + graph algorithms + import validation.

If a function never reads or writes a ref, it has no reason to live inside defineStore.

  • Belongs in the store: reactive state and the thin mutations that wire pushHistory() to a state change (addNodeAt, deleteSubtree, setLabel, moveNode, reparent), plus undo/redo + persistence.
  • Was hitching a ride (pure functions): the traversal cluster (nodeById, rootNode, childrenOf, ancestorsOf, levelOf, descendantsOf), the angle-placement search in addChild, and the importJSON normalization.

The high-value, low-risk move was extracting the traversal cluster — done (see the refactor log).
